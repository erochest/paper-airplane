# 08: Pi Sessions

**What to build:** Everything that works in a Claude Code Session also works in a Pi Session. `fly reply`, `fly replies` and `fly conversation` read Pi's transcript and follow only the current branch of Pi's session tree, so abandoned branches never appear.

**Blocked by:** 05, 07

**Status:** ready-for-agent

- [x] The Session is located from `PI_SESSION_FILE`, and the host (Claude Code or Pi) is detected from the environment.
- [x] The current branch is rebuilt by walking `parentId` back from the leaf entry.
- [x] Only `user` and `assistant` message text is kept. Thinking, tool calls, tool results and other entries are dropped.
- [x] The Session Title comes from Pi when it provides one, otherwise follows the same rules as ticket 04.
- [x] Long Reply selection, `--reply` references, resend protection and Conversation styling behave exactly as for Claude Code.
- [x] Unrecognised entry shapes cause a clear, loud error.
- [x] Scrubbed Pi fixtures include a Session with abandoned branches and trailing short Replies.

## Comments

- Implemented. Notes for later tickets:
  - The reader follows Pi 1.1.x (session format version 3), checked against Pi's `docs/session-format.md`, `docs/message-types.md` and `dist/core/session-manager.js`. It parses all 63 local Pi sessions without error.
  - The leaf is the last entry in the file, which is how Pi's `SessionManager` picks it on load. When `fly` runs, the agent's own tool-call message has just been appended, so the leaf is on the current branch.
  - The Session ID is the session header's `id`. Reply references are entry ids (8 hex characters). As for Claude Code, a Reply is every assistant `text` block from one prompt to the next. Its reference is the entry holding its first text block, and its timestamp is that of its last text block.
  - The Session Title from Pi is the latest `session_info` name anywhere in the file, on any branch, trimmed, with an empty name meaning cleared. This matches Pi's `getSessionName`.
  - `/skill:name args` is shown as typed. The skill body Pi expands it into is left out, using the same pattern as Pi's own HTML export.
  - Dropped: `toolResult`, `system`, `bashExecution` (commands run with `!`), `custom` and `custom_message` (extension-injected), `compaction`, `branch_summary`, `context_edit`, `label`, `usage` and settings entries. Compaction needs nothing special, because Pi keeps the summarised entries on the branch.
  - Shape checks apply only to the current branch. Entries on abandoned branches are never read, so an odd entry there doesn't break a send.
  - Host detection:
    - `PI_SESSION_FILE` means Pi.
    - `PI_SESSION_ID` without a file is an ephemeral Pi Session, and is refused clearly.
    - If a Pi variable and `CLAUDE_CODE_SESSION_ID` are both set, one agent was started inside the other, and `fly` refuses to guess.
  - Open decision: Pi's docs say consumers "should tolerate unknown custom roles" that extensions add. Following this ticket, an unknown role is a loud error, so an extension that persists its own role would make `fly` fail for that Session. If that turns out to be a nuisance, skip unknown roles instead.
  - Not handled: a prompt that is only images becomes an empty "You" block in a Conversation Dispatch (the same as for Claude Code).
  - The Reply-grouping loop is duplicated in `claude-code.ts` and `pi.ts`. It is small, but it could become a shared helper if a third host arrives.
  - Fixtures are generated by `test/fixtures/pi/generate.ts`.
